# magicdub-cli 上下文约束时长改写改造计划

状态：策略已确认，源码改造与自动化验证已完成，并已正式发布 v0.4.0（7a7a608）；日常安装尚未升级。用户选择在后续实际使用中长期观察，不做本次样片验收。本文保留实施方案与完成证据，不替代 Release。

## 1. 已确认与本轮范围

- 用户决定继续使用 `deepseek-flash`，在程序侧改善时长改写后的跨句衔接；保持纯 CLI，不接入 agent、不微调、不切换 GPT 模型。
- 本轮按最近讨论的简化方案展开：程序准备全文与当前译稿；LLM 只编辑指定句子；程序负责校验、版本、次数、TTS 与选稿。
- 默认沿用合格区间 `[0.8, 1.2]` 与最多两次改写，实际读取并传入任务冻结的 `run.fitting`，不在提示词另写死阈值。
- 首译继续全句一批；改写继续每轮收集所有未选定句，一次请求批量处理。同轮先全部 TTS、再全部 duration_fitting；全部选定后 alignment。
- 第一版不增加独立语义审校调用、自动全文润色、模型自动全局选稿、术语抽取模型或长文摘要管线。上下文连续是首译与每次改写必须遵守的生成约束；程序没有把这一要求误记为已经通过语义验收。
- 用户确认每轮必须保持上下文连续，在此基础上仍按时长选稿。三轮未进入区间时保持原有最接近时长选择，不采用首稿回退政策。

代码核查基线：`shishengkai/magicdub-cli@7c576d751d08a513f10768f1d56eb1867c2572e3`。改造前已核实有全文原文、没有当前目标译稿与语义选稿检查；详见 [诊断记录](../../.records/events/2026-09/2026-09-29_151321_核查CLI时长改写缺少目标译文上下文与语义选稿.md)。

## 2. 改造步骤

### A. 构造一轮固定的全文上下文

translation slot 在每轮调用开始前，从 state 构造只读快照，不依赖 API 会话记忆：

- 完整原文，按稳定句子 ID 附带说话人、时间窗。
- 首轮完整译稿：各句 attempt 1，保留为不可覆盖的表达基线；它不是已通过语义验收的金标准。
- 当前译稿：已有 `selected_attempt` 的句子用已选版本；仍未选定的句子暂用首轮译文，并标明是临时候选。这一确定性规则避免把“最近生成”误认为“已采用”。
- 本轮可编辑 ID 白名单；其余译文固定，只供参考。
- 对每个可编辑句额外突出前后各 2 句的原文与当前译文；保留说话人边界，相邻待改句作为同一窗口阅读。窗口只是显著提示，不替代全文。未选邻句同时提供历史候选，要求本句可独立替换，兼容不同轮次混选；已选邻句只把已选版本列为可保留候选。
- 每句首轮文本、所有已完成的历史尝试、实测 TTS 时长及 ratio，以及允许的最短／最长时长。

同一轮所有修改基于同一个快照，候选返回后才写 state。第三轮重新构造快照，看到第二轮已选定的邻句。未选句仍以首译为基线，历史失败用于避免重复；不要求模型在第二轮措辞上继续累积修改。

本轮以已有短视频范围传入完整上下文；请求过长时明确失败，不静默截断全文、不自动换模型或用摘要代替。

### B. 改写指令改成最小必要编辑

首译强调连贯的口语表达及固定句子／时间窗的信息归属；第二、三轮针对首轮基线提出有限修改，参考当前邻句和全部尝试历史。

优先级：忠实原意与跨句衔接 → 尽量进入允许时长区间 → 减少不必要的措辞变化。目标是进区间，不强求 ratio=1。

显式约束称呼、指代、术语、时态、语气、否定、条件、因果、关联词配对与问答关系；不把信息移入或移出相邻句；不为加长编造解释或填充语。ASR 切成半句时，以上下文理解，但仍只修改指定片段，不改时间窗。

允许在无法安全改善时原样返回该句基线文本；“没改文字”不能被标记为语义已验收或时长达标。模型输出继续是 `translations: [{id, text}]`，不要求模型返回自评分、隐含推理或管理版本。

### C. 本地校验与相同文本处理

- 返回 ID 必须与可编辑 ID 集合完全一致；拒绝遗漏、重复、额外 ID、空文本和不符合约定类型的字段。
- 先校验完整一批，再提交本轮文本；失败不把半批结果混入 state。
- 对输出作现有必要的首尾空白清理后，按文本精确相等识别本句已有尝试；不凭语义相似、删除标点或跨句相同文本来复用音频。
- 返回本句已有文本且对应音频引用、哈希和冻结 TTS 条件有效时，复用其音频，沿用统一测时长步骤重新测量，记录来源；不新增一次虚构 TTS 请求或重复费用。
- 验证可复用的相同文本／原样保留时终止该句后续改写，按已有候选的最接近时长选稿；其他未完成句继续原轮次流程。相同文本但音频无法验证时重新生成 TTS，不伪造复用。
- 文字变化才请求新 TTS；音频复用只限同一任务、本句、相同声音参考与 TTS 条件，不扩展跨任务缓存或续跑能力。

### D. 选稿与证据

时长合格后选用、轮次上限后兜底仍由 pipeline 控制。第一版没有独立语义判断器，不能让 `fitting_pass` 等同于“翻译质量通过”。

三轮都未达标时，保留既有规则：先比较到允许区间的距离，再比较到 ratio=1 的距离，仍并列时取较早尝试。时长失败只触发这一确定性选稿；不新增语义评分排序，也不声称提示词能保证模型绝不违约。

任务中保留提示词版本、每轮上下文快照、请求 ID 范围、返回译文、改写／复用／提前结束原因。不得保存 API Key、鉴权请求头或模型内部推理。translation 调用有已知 usage 就保留其费用，包括内容校验未通过的响应；复用音频不计新 TTS 费。每次 HTTP 响应按请求序号分别保存，不把“最多两次改写”误报为最多三次 HTTP 请求。完成但内容损坏的响应保留费用并失败，不再原样重复付费请求；可重试 HTTP 状态仍沿用有界重试。

## 3. 模块边界与交付顺序

| 位置 | 改动责任 |
| --- | --- |
| `steps/slots/translation.py` | 组装规范化上下文、ID 集合和冻结区间；整批验证后落 state；保留费用与引用 |
| `adapters/translation/deepseek_deepseek_flash/` | 首译／改写消息、JSON 内容解析；继续调用 deepseek-flash；模型只生成文字 |
| `pipeline/runner.py` | 原轮次调度、重复文本的提前结束、最终兜底政策和选稿原因 |
| `steps/slots/tts.py` | 同任务本句完全相同文字的音频复用校验；真实 TTS 请求与费用 |
| `state/` 与测试 | 必需的可选溯源字段、原子提交和兼容默认值；不迁移旧任务 |
| `steps/fixed/duration_fitting.py` | 保持纯时长测量，不承担翻译或审校 |

实施顺序：上下文纯函数与测试 → adapter 提示词与输出校验 → slot 批量提交和留痕 → 重复文本／兜底调度 → 集成回归，以上本地完成。真实质量由用户后续长期使用观察；Git 与 v0.4.0 发布已随后完成，正式规范同步与日常安装升级独立处理。

新增元数据优先采用兼容的可选字段，不为此次改造重做整个 state schema。具体字段名、邻句窗口大小、测试组织由实现解决，不需用户逐项批准。

Git 提交、推送、tag／Release 已根据用户后续明确授权于 v0.4.0 完成；日常安装升级仍独立处理。本轮不改分离、ASR、TTS 模型、时间窗、混音或成片命名。

## 5. 验证计划与完成标准

离线／受控测试覆盖：

1. 第二轮包含完整原文、首译、当前译稿；第三轮准确引用第二轮已选定邻句，未选句使用明确基线；说话人、ID、顺序与历史一致。
2. 多个相邻或不相邻失败句仍一次批量请求；不可编辑句不会被输出覆盖。
3. 自定义 fitting 区间传入提示词；指令不追求单一 ratio=1、不引入固定字／秒公式。
4. 额外／重复／缺失 ID、空文本、JSON 损坏与半批结果不会污染 state；已知请求费用保留。
5. 原样或重复文本不重复 TTS、不重复费用；语音条件或文件不匹配时不能错误复用；提前结束后其他句仍继续。
6. 两次改写上限、已选句不返工、兜底政策、TTS 与 duration_fitting 的阶段顺序、最终字幕／音频版本一致。

按用户最新决定，本次不运行真实视频、不调用付费 LLM／TTS、不要求提供验收目录。后续使用若再次出现衔接问题，可利用已保存的轮次上下文、候选和时长，定位是模型违反上下文约束、ASR／分句问题，还是独立选稿后的组合问题，再按事实决定下一步。

本次工程完成标准：离线与相关回归通过，确定性流程及版本对应关系有测试证据；真实翻译、声音与成片质量不作已通过结论。
