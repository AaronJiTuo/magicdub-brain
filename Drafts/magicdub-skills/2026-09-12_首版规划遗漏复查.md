# magicdub-skills 首版规划遗漏复查

用户认可上一轮交互式安装配置与独立维护 skill 方案，并要求再检查遗漏。本次检查正式规划、CURRENT、五篇相关设计 Draft，并只读核验两段指定媒体；不修改被检查的设计内容，不调用模型或安装软件。以下为检查发现与建议，不等于全部成为新的已确认需求。

## 1. 结论与优先级

未发现必须再次更换技术路线或新增 skill 的理由。安装配置、升级和译制的职责可以保持；下一步重点是补齐少数运行规则、验证现有模型组合并统一正式规划。已有原件复制、双币种费用、强制对齐、质量问题自动继续、模型选择和跨平台分期不重新开题。

| 项目 | 当前文档情况 | 优先级 |
| --- | --- | --- |
| 停止、继续与宿主退出 | 已有 run / attempts / needs_agent 和恢复基础；尚无面向用户的停止与继续契约 | 首版实现前明确 |
| 多音轨输入与导出 | 已有选中音轨字段和独立输出；尚无具体选轨、输出轨和画质处理默认规则 | 首版实现前明确 |
| 配置来源与覆盖顺序 | 已有全局配置、项目快照与凭据分离；优先级及冲突提示未定 | 首版实现前明确 |
| 清理与卸载 | 已有缓存与用户资料分离、磁盘检查；文件保留和清理边界未定 | 首版保留数据，清理功能可后置 |
| 多人及长片模型组合 | 已明确全局说话人、声音参考、分块、重叠和背景音要求；未形成当前候选组合的集成证据 | 优先实测，不靠新增规划替代 |
| 对外验收与正式规格 | 安装自检、费用与媒体验收已规划；多人 / 两小时 / 多音轨覆盖不足，正式 Release 仍有冲突 | 开工和声称支持前分别闭环 |

## 2. 需要补齐的运行规则

### 停止与继续

- 建议“停止”表示不再提交后续步骤，保存本地进度；已提交的远端任务记录请求编号和已发生费用，不能把本地停止写成远端已取消。远端取消只有取得实际结果才记录成功。
- “继续”先读取原 run、查询尚未明确的远端状态并复用已下载的结果；“重新做”另建 run，费用与历史分开。提交结果不明时先核对，不能无条件再次提交；无法核对时如实记录技术失败与待核实费用，不增加质量审校门槛。
- 两个 Codex 任务指向同一视频项目时，使用现有单写者设计阻止重复启动或覆盖；仅凭锁文件存在不能判定进程仍在运行，恢复需核对锁实际持有状态。
- 从当前“程序与宿主 LLM 分批交接”的设计推导，不能承诺关闭 Codex 后整片仍自动完成。建议首版支持当前任务内持续推进和中断后续跑；本地进程、云端执行、等待 agent 的状态分别保存。恢复时不能把 needs_agent 误当成模型接口失败反复重试。

### 多音轨与输出

- 电影输入需识别全部音轨，展示语言、声道、轨道编号和默认标记。已有明确选择直接采用；有多条可能的对白音轨且无法确定时才提供选择，不能静默取第一条。
- 建议成品以目标语言译制轨为默认播放音轨，配音与背景轨混合时不再次叠加完整原对白。是否额外保留可切换原声轨作为可选导出参数，原始文件副本始终保留。
- 输出容器、视频编码与声道规则需定稿。建议优先保留原画面、分辨率、帧率和时间轴；能保留原视频流则避免无谓重编码，不兼容时按已公布的兼容导出方案转换并报告。
- 有内嵌字幕、章节或封面时需明确保留策略；首版不生成字幕不等于可以默认烧录来源字幕或声称保留所有附属轨。此项不是新增字幕制作功能。
- 临时导出通过可读性、音视频轨、起止时间和时长核验后才成为成品；不以文件存在或合成进程退出为唯一成功依据。

### 配置优先级

- 建议非敏感参数按“本次明确指定 → 视频项目设置 → 用户全局默认 → 程序默认”解析，并保存最终实际参数；恢复旧 run 使用该 run 的快照，明确改模型或重做时建立新的运行关联。
- 凭据来源独立处理。环境变量与本地凭据文件同时存在时，需固定优先级并只显示实际来源，避免 setup 改了本地 key，程序却继续使用旧环境变量。不能把凭据值写进项目快照。
- setup 的可用状态还应标明费用统计能力：能否按请求对账、仅可估算或金额待核实。普通 API 鉴权通过不等于所有费用查询已可用；沿用现有账本方案，不新增预算控制。

### 清理与卸载

- 建议默认保留原件、文本修订、说话人参考、付费生成结果、账本和成品；先只自动清理明确可安全重建的下载 / 解包临时文件。
- “可重新生成”不代表“应自动删除”：重新调用模型会再次花费的产物不能作为普通无成本缓存清理。活跃任务引用的文件不删除，远端结果本地验证完整后才视为已保全。
- 日后增加卸载时，默认仅移除 MagicDub 自身入口和受管理程序，保留用户配置与视频资料；删除资料应是明确独立范围。当前无需为了首版提前开发完整清理器或卸载 skill。

## 3. 已考虑，但最需要实测的链路

多人问题不是只在 JSON 加 speaker_id。需要验证所选 ASR / 分离组合如何形成说话人区分、跨块映射、每人声音参考与 TTS 调用，并检查同一人的音色在长片中是否一致。多人同时讲话时，逐句强制到原窗口仍需能表达重叠，不能为了实现方便直接串行拼成更长的电影。

目前 Draft 已列出上述目标，但没有新 skill 的模型调用证据。本次不根据候选名称宣称能力齐全或新增供应商；建议优先用小型多人片段做集成验证，再完成原定两段完整视频和约两小时长片验证。候选缺少所需能力时明确适配缺口，不静默换模型。

全片人名、术语和上下文一致性已被提及，实施时应将可复用映射落盘、分批交给宿主 LLM；不能只放在某轮聊天里。后续字幕直接复用选定译文修订，避免字幕 skill 另翻一遍形成不同用词。

## 4. 本次只读证据与验收缺口

2026-09-12 再次通过 ffprobe 核验：stevejobs.mp4 为 885.191111 秒，trump_full.mp4 为 1790.072744 秒；两者均为一条 H.264 视频轨和一条 AAC 双声道音轨。本次没有试听，也不以音轨数推断说话人数。

现有媒体不能提供多音轨选择或两小时处理的直接验收覆盖；多人交替、重叠说话、复杂背景和声音一致性仍需明确场景证据。保留指定两段验收素材，不以小片段替代完整验收。

除媒体质量外，需要实际验证全新 macOS 安装、未配置直接发起译制、任务中断续跑、重复请求不重复收费、已有项目经升级仍能使用。相关方向已有设计，当前缺的是执行证据；不能继续用增加文字替代这些验证。

## 5. 开工前统一正式规格

[旧 Release](../../Releases/05_magicdub-skill项目规划.md)仍写一个 skill、一套默认模型、模型选择后置、多人短样本优先，技术栈未定，并要求明确 API 预算。它与最新已确认的三 skill、候选选择、多人 / 长片、Python 3.12+ 和不设预算要求有冲突。

这种漂移已在 CURRENT 标记，本次再次确认存在。建议在进入实现前将已确认决定整理进一份正式规划；本轮是检查任务，因此不改写 Release。文件名称、默认根目录和安装依赖来源等小项可以随实施收敛，不必再开展一轮没有截止点的功能规划。
