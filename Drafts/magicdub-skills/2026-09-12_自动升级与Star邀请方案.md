# magicdub-skills 自动升级与 Star 邀请方案

用户已要求加入类似 brain-template 的自动升级与请求 Star 功能，并进一步要求将安装配置、升级从主 skill 拆为独立入口。本文按 [安装配置与拆分方案](2026-09-12_交互式安装配置与Skill拆分方案.md)更新职责；功能及拆分方向已确认，以下具体策略为设计建议，尚未实现或进入正式 Release。当前阶段仍以首个译制 skill 可用为优先，不因维护功能提前开发完整 plugin。

## 1. 功能归属与触发

- 版本检查与升级由独立升级 skill 负责，建议命名 `magicdub-upgrader`；首次安装与配置由 `magicdub-setup` 负责，配音业务保留 `magicdub`。底层程序仍由整个集合共用，不按配音、字幕复制升级逻辑。
- 上一轮“不必新增独立 skill”的建议已被用户本轮拆分要求替代。用户可以在当前工作流中说“检查 MagicDub 更新”或“升级 magicdub-skills”，由 agent 按需读取升级入口，不必手动切换。业务 skill 只保留轻量检查与路由规则，不载入完整维护长文。
- 按 brain-template 的语义设计为：自动检查新版并提示；用户明确要求升级后自动完成普通升级，不再进行第二轮相同确认。自动发现新版本身不触发覆盖安装。
- 自动检查放在任务结束、已输出成品位置或失败状态和 `$金额 + ¥金额` 费用报告之后；设置短超时，并建议同一安装每天最多自动查询一次。显式检查命令不受该缓存限制。
- 没有新版或后台检查失败时保持安静；显式检查失败则说明原因。用户禁止联网时跳过自动检查。不增加常驻服务、定时任务，也不在每句、每个模型步骤结束时重复检查。

## 2. 升级来源与版本

- 固定更新源为 `github.com/shishengkai/magicdub-skills`，默认只跟踪正式稳定 GitHub Releases；过滤草稿与预发布，按 `vX.Y.Z` 的 SemVer 选择最高版本。
- 建议正式发布采用不可变 Release。将 tag 解析到精确 commit SHA，核验同一 SHA 下的发布清单、版本和文件校验信息；不使用浮动 `main` 作为稳定升级目标。
- 自动检查阶段只读发布元信息，不执行远端程序。发现新版时展示当前版本、目标版本与主要变化，供用户决定何时升级。
- 首版采用技能集统一发布版本，业务 skills 与共享程序按兼容组合更新；记录用户安装的组件集合，不自动增加未选择的业务 skill。
- 安装记录至少包含来源、版本、commit SHA、安装方式与已安装组件。项目数据格式的 `schema_version` 独立于软件版本；升级软件不等于自动升级所有视频项目格式。
- 私有阶段只使用使用者已有的仓库访问权限；不能读取更新源时仍允许使用已安装版本，不把公开仓库、GitHub 登录或 Star 作为译制条件。

## 3. 用户要求升级后的执行

1. 确认当前安装方式和目标稳定版本，给出范围说明后继续，不重复询问普通升级确认。
2. 下载到临时位置，核验目标 SHA、文件和依赖；检查当前安装是否有用户修改。不能直接用强制覆盖或 `git reset` 丢弃本地改动。
3. 保留旧版本，再切换到验证通过的新版本。失败时继续使用旧版本；升级检查和本地自检不调用付费模型 API。
4. 配置、密钥、视频原件、中间产物、用户改过的译文、已导出的成品与费用账本均不被代码升级覆盖。模型选择和已有任务参数继续采用项目快照，不因新默认值改变。
5. 每个 run 记录实际执行的 skill / 程序版本。已有任务使用原版本完成；新版本用于后续任务。实现方式需验证能否并存旧运行环境；若不支持并存，则等待活动任务结束再切换，不替换正在执行的文件。
6. 恢复旧项目时校验数据版本与兼容性。需要迁移时保留原数据和可用旧运行版本；未提供可靠迁移方案时不能靠覆盖项目文件强行升级。
7. 验证实际加载的 skill 和程序版本，说明是否需要重新加载或新开任务。只下载了新版、宿主仍加载旧版时，不能报告升级已生效。

上述机制由安装程序负责。存在无法保留的本地修改、破坏性数据迁移或其他超出普通升级范围的问题时，才单独说明需要处理的具体差异。

## 4. 独立 skill 与未来 plugin

| 安装方式 | 建议的维护责任 |
| --- | --- |
| 由 MagicDub 安装程序管理的独立 skills | 使用自身升级器更新受管理文件和兼容依赖 |
| 开发者源码 checkout / 手工安装 | 可以检查版本；不能假定目录归升级器管理，也不自动 pull、切分支或覆盖未提交修改 |
| 将来的 Codex plugin 安装 | 交由宿主支持的安装 / 刷新机制处理，MagicDub 不自行改写宿主管理的 plugin 缓存；更新后验证实际加载版本 |

当前 Codex 官方文档说明，plugin 使用安装后的缓存副本，并提供 marketplace 管理与刷新机制；刷新 marketplace 元信息本身不能当作 MagicDub 新版本已经加载的证据。这个边界用于未来适配，首版不需要提前实现 plugin 更新通道。来源：[Build plugins](https://developers.openai.com/plugins/build/plugins)，2026-09-12 核对。

安装清单、更新检查缓存等维护状态放在用户级应用数据中，与配置和视频项目的分离原则一致；跨平台具体路径仍随安装方案一起定稿，不在此固定为某个 `~/.magicdub/` 子目录。

## 5. Star 邀请

- 固定邀请对象为 `shishengkai/magicdub-skills`。结合独立 setup / upgrader，建议在首次安装配置全部成功、或成功升级后判断是否邀请；同一次成功事件最多一次，由两者复用一份公共规则，不另设 Star skill。普通译制、配置修改、自检、重复安装及失败不邀请；该建议替代上一轮首个视频完成后邀请的设想。
- 推荐仅在仓库公开、当前使用环境适合且尚未 Star 时邀请。作者开发 / 自用场景默认不邀请；用户已表示不再提醒时尊重该偏好。不能每次导出、每个阶段或每个业务 skill 都询问。
- 邀请在任务成果与费用报告、或升级结果之后提出，可以直接忽略；Star 不影响功能、模型选择、更新、验收或成品获取。
- 已有可用 GitHub 身份时，只读判断是否已 Star。检查不可靠、工具不可用、未登录或已 Star 时跳过自动操作邀请，不要求用户为此安装工具、登录或提供凭证。用户主动要仓库链接时仍可以提供普通链接。
- 实际 Star 操作前明确仓库和当前 GitHub 账号，只有针对这次邀请的明确同意才执行；“升级”“继续译制”或其他流程的确认不构成 Star 授权。
- 执行后回读确认 Star 状态，失败如实说明，不影响已完成的译制或升级。不同意、忽略或 Star 失败不创建视频项目记录，也不记入费用账本。
- 邀请频率控制与“不再提醒”偏好只存本地用户级维护状态，不把账号和互动记录写进源码仓库或视频项目，不增加遥测服务。

## 6. 首版实施与验收建议

首版即划分安装配置、升级与译制 skills，预留版本与安装来源记录，并随首个可安装稳定版本落实基本检查、升级和可选 Star 流程。安装命令、发布清单格式与检查间隔在实现时收敛；不用先完成 plugin、自动迁移所有历史项目或后台更新服务。

最小验收应覆盖：

- 只识别有效稳定版本；无新版、网络失败、私有仓库无权限不影响视频任务与费用报告。
- 用户一次明确升级指令可以完成普通更新；本地修改得到保全，失败可继续使用旧版本。
- 正在处理的视频不混用程序版本；配置、素材、译文、成品和费用账本在升级后保持有效。
- 新版加载状态可核验；软件升级与项目数据迁移分开处理。
- 没有明确 Star 同意时不产生 GitHub Star 写操作；已 Star、拒绝、忽略和认证失败均不阻塞核心功能。
