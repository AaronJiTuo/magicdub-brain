# checkpoint-recorder

## 什么时候使用

当工作已经形成重要决策、实质成果或项目状态变化时，使用本流程主动留痕，无需等待用户额外说“记录一下”。典型触发包括：

- 用户明确确认或否决了会影响后续工作的方案。
- 形成或选定了文案、内容、产品设计、界面设计等实质成果。
- 软件行为、版本、接口、数据结构或工程状态发生实质变化。
- 完成发布、部署、迁移、回滚或基础设施配置变更。
- 得出会影响后续工作的根因、限制、风险或验证结论。
- 项目阶段、当前状态、阻塞条件或下一步发生重要变化。

判断标准是：**如果未来的 agent 不知道这件事，是否可能重复劳动、误判状态或采取错误行动？** 如果是，应创建检查点。

## 用户授权与优先级

- 用户明确说“本次不要记录”“不要落盘”“只在对话中回答”或“完全只读，包括 brain”时，不创建 Draft、Record 或更新 `CURRENT.md`。
- 用户说“只讨论”时，纯探索内容不落盘；如果用户随后明确要求形成项目成果，再按本流程判断。
- 用户说“检查一下”时，不修改被检查对象；但允许把重要诊断结论写入 brain。用户明确要求 brain 也只读时除外。
- 冷启动项目在身份、范围和约束经用户确认前不自动留痕。确认后可以建立第一份状态基线。
- `brain-template` 权威模板仓库自身是脚手架例外：当 `Releases/` 仍只有模板说明、项目专属约束仍是占位内容时，`.records/` 必须保持为可复制的空白初始状态，不为模板开发过程创建项目事件；协议版本与 Git 历史承担模板自身的变更证据。
- 用户对具体任务的明确要求高于本 skill 的默认规则。

## 哪些情况不记录

- 普通头脑风暴、尚无结论的探讨和临时举例。
- 每条命令、每次失败尝试、每次测试重跑或过程性进度播报。
- 不改变含义的格式、措辞和像素级微调。
- 已被同一结果级 Record 完整覆盖的细小步骤。
- 已存在相同结论且状态没有变化的重复信息。
- Record 的创建、整理、校验或 Git 交付过程本身；禁止递归产生 Record。

## 先判断是否需要保全成果

Record 只保存事件摘要，不能替代成果本身。

### 只创建 Record

以下情况通常只需创建 Record：

- 简短决策、发现或状态变化。
- 成果已经完整存在于 `Drafts/`、`Releases/` 或外部工程中。
- 外部工程已经包含实现，只需引用稳定仓库地址、commit、版本或成果位置。

### 先保全成果，再创建 Record

如果实质性文案、文章、产品设计、界面方案或其他可复用成果只存在于当前对话中：

1. 先读取并执行 `.skills/draft-organizer/SKILL.md`。
2. 将当前有效成果保存到 `Drafts/`；不保存每个试错版本。
3. 具有独立价值的备选方案可以保留，并清楚标注状态。
4. 再创建 Record，引用该 Draft。

自动保全默认只进入 `Drafts/`，不得据此擅自修改 `Releases/`。只有用户明确要求更新 Release、原任务已经包含 Release 更新，或当前任务本来就是维护既有 Release 时，才执行 `.skills/release-organizer/SKILL.md`。

## Record 类型

`kind` 使用以下值之一：

- `decision`：明确确认或否决的决策。
- `artifact`：形成、选定或更新的实质成果。
- `state_change`：项目、工程或外部系统的状态变化。
- `finding`：会影响后续工作的发现、根因、限制或风险。
- `milestone`：阶段成果、发布、部署或交付。
- `handoff`：需要持续保留的当前状态和下一步交接。

`domain` 使用最贴近任务的值：

- `product`
- `content`
- `design`
- `engineering`
- `infrastructure`
- `operations`
- `other`

`certainty` 使用以下值之一：

- `confirmed`：用户或当前权威文档明确确认。
- `verified`：agent 已通过直接证据验证。
- `reported`：来自用户或第三方陈述，尚未独立验证。
- `tentative`：暂时判断，仍需确认。

不得把 `reported` 或 `tentative` 写成已经验证的事实。

## 文件与元信息格式

事件路径使用：

```text
.records/events/YYYY-MM/YYYY-MM-DD_HHMMSS_可搜索主题.md
```

同一秒存在重名风险时，在文件名主题后追加短随机串。文件名时间用于检索，不作为唯一身份。

每条 Record 至少包含：

```yaml
---
record_id: rec_20260812_153000_a1b2c3
occurred_at: 2026-08-12T15:30:00+08:00
kind: decision
domain: product
certainty: confirmed
related_artifacts:
  - Drafts/首页文案/2026-08-12_第二版.md
supersedes: null
---
```

- `record_id` 使用时间戳加随机后缀，必须在当前仓库中唯一。
- `occurred_at` 使用带时区的 ISO 8601 时间。
- `related_artifacts` 只写 brain 内相对路径、去除凭证的稳定网络地址或外部工程的稳定标识；禁止写本机绝对路径和要求协作者采用同一目录结构的 `../xxx` 路径。
- `supersedes` 在更正旧记录时填写旧 `record_id`，普通记录为 `null`。
- 没有关联成果时，`related_artifacts` 使用空数组 `[]`。

正文建议使用以下小节，没有内容的部分可以省略：

```md
# 简短、可搜索的事件标题

## 结果

## 背景与理由

## 证据与成果位置

## 对当前项目的影响

## 未完成与下一步
```

## 执行步骤

1. 判断是否达到检查点。
   - 已经形成结果，而不只是探索过程。
   - 未来 agent 不知道它会产生实际损失。
   - 用户没有关闭本次留痕。

2. 查重并确定粒度。
   - 先查看 `CURRENT.md`、相关文件名和必要的相关 Record。
   - 不要为了查重全文扫描所有历史事件。
   - 同一连续工作阶段的细小动作合并为一条结果级 Record。

3. 必要时保全成果。
   - 对话中独有的实质成果先保存到 `Drafts/`。
   - 已存在于其他位置的成果只引用，不重复复制。

4. 创建事件文件。
   - 使用唯一 `record_id`、准确时间、合适的类型、领域和可信度。
   - 记录结果、理由、影响、证据位置和仍未完成的事项。
   - 默认控制在一页以内。

5. 更新 `.records/CURRENT.md`。
   - 只更新受本事件影响的小节。
   - “最近关键变化”通常保留 5 至 10 条，旧内容仍可从 events 追溯。
   - 删除或替换已经不再成立的当前状态，不把历史过程累积在 CURRENT 中。
   - Release 与实际状态不一致时，在“文档与实际状态漂移”中明确标记并链接证据。
   - 在“相关记录”中只保留仍影响当前工作或支撑当前状态的少量链接。

6. 复核。
   - Record 不依赖完整聊天或未保存的临时输出才能理解。
   - 可信度与证据强度一致。
   - 没有敏感信息、本机路径或大段原始材料。
   - 没有因为创建 Record 再创建一条 Record。

7. 向用户说明。
   - 最终回复简要说明本次保存了哪些成果和 Record。
   - 当前协议不自动执行任何 Git 操作；若用户没有另行要求，不提交也不推送。

## 更正与状态漂移

- 历史事件原则上不可变。发现旧记录错误时，新增一条更正 Record，并用 `supersedes` 指向旧记录。
- `CURRENT.md` 反映最新有效状态，不需要保留已经被更正的错误描述。
- Release 说明“应该是什么”，`.records/CURRENT.md` 说明“现在怎样”，`.records/events/` 保存“发生过什么”。Release 与 CURRENT 冲突时记录漂移，并用相关 Record 保存变化证据，不静默修改任何一方。
- 从 Record 更新 Release 时执行 `.skills/release-organizer/SKILL.md`。Record 即使已被 Release 吸收也继续保留，不移动、不删除。

## 安全与容量边界

禁止写入 Record：

- 密码、令牌、密钥、完整 Cookie、完整 `.env` 或其他凭证。
- 带有用户名、令牌或签名参数的认证 URL。
- 完整聊天记录、模型思考过程、终端日志、diff、云审计日志或大段工具输出。
- 与结论无关的个人信息、临时调试信息和可从正式成果直接获得的重复全文。

Record 保存“结论与如何找到证据”，不复制证据本体。二进制成果、大型附件和生成物遵循项目原有存储策略，不直接塞入 `.records/`。

## Git 与外部工程红线

- 本 skill 只负责留痕，绝不自动执行 `git add`、`commit`、`pull`、`fetch`、`rebase`、`merge`、`push`、tag、release 或 PR 操作。
- 不得以留痕为理由，对当前 brain 或任何关联代码库执行 Git 写操作。
- 关联代码库可以作为只读证据源读取仓库地址、commit、版本、状态和验证结果，但不得自动提交或推送。
- 用户另行明确要求 Git 交付时，将其视为独立任务，遵循该任务的授权与安全边界。

## 禁止事项

- 不要把 `.records/` 当作逐命令流水账或完整聊天归档。
- 不要为了理解项目而全文扫描 `.records/events/`。
- 不要把未验证判断伪装成已确认事实。
- 不要仅创建“完成了某成果”的 Record，却不保存对话中独有的成果本身。
- 不要因自动保全而擅自修改 `Releases/`。
- 不要回写、删除或移动历史 Record；通过新增更正记录纠错。
- 不要让 Record 创建流程递归触发自身。
