# draft-organizer

## 什么时候使用

凡是 AI agent 要在 `Drafts/` 中创建、续写、移动或整理文件时，必须先使用本流程。典型触发包括：

- 用户要求“落一份 Draft”“把讨论整理成草稿”。
- 其他 skill 将内容保存到 `Drafts/`，例如 `chat-capture`。
- `checkpoint-recorder` 判断对话中已经形成需要保全的实质成果。
- 新 Draft 与已有 Draft 属于同一件事或同一方面。
- 用户要求写验证脚本、测试页面、可运行原型或其他程序。
- Agent 在本次相关范围内发现同一主题的文件已经较多。

纯探索讨论默认不落盘。以下任一授权成立时，本 skill 决定文件应放在哪里：

- 用户明确要求写入 `Drafts/` 或创建项目成果文件。
- 用户要求完成文案、内容、设计等实质成果，且成果已经形成、只存在于当前对话中；这属于 `.skills/checkpoint-recorder/SKILL.md` 的成果保全。

用户明确说“本次不要记录”“不要落盘”“只在对话中回答”或“完全只读，包括 brain”时，以上成果保全授权失效。

## 两条硬规则

### 1. 普通 Draft：同主题达到 3 个文件时归组

- `Drafts/` 根目录是临时收件箱，只保留单篇、尚不足以成组或暂时无法可靠归类的普通 Draft。
- 如果已经存在匹配的主题目录，新 Draft 直接写入该目录，不再写到根目录。
- 如果根目录中与新 Draft 明确属于同一主题的文件，在加入新文件后达到 3 个，则创建 `Drafts/<主题关键词>/`，把这些相关文件一起移入。
- 少于 3 个文件时不要为了整齐强行建主题目录，除非用户明确要求。

### 2. 程序与可运行原型：从第 1 个文件起独立成目录

- 任何程序、验证脚本、测试页面、可运行原型或代码实验，即使只有一个源码文件，也禁止直接平铺在 `Drafts/` 根目录。
- 一个程序必须完整放在一个独立目录中，源码、配置、测试数据和运行说明不得散落到其他 Draft 目录。
- 新程序使用 `Drafts/<程序或验证主题>/`。
- 如果程序明确属于一个已有主题，可使用 `Drafts/<主题关键词>/<程序或验证主题>/`；程序目录是主题目录下允许的二级目录例外。
- 续写同一个程序时复用已有程序目录，不要按日期反复创建新目录。
- 新程序目录应包含简短的 `README.md`，至少说明用途、运行方法、预期验证结果和当前状态。

“程序”包括但不限于：

- `.py`、`.js`、`.ts`、`.sh`、`.php`、`.go`、`.java` 等可执行源码或脚本。
- 用于交互测试或验证的 `.html` 页面。
- `package.json`、`requirements.txt`、`Dockerfile` 等程序运行清单。
- 带有源码、依赖和运行步骤的原型目录。

仅在 Markdown 文档中展示的一小段示例代码不算独立程序，不需要因此建程序目录。

## 执行步骤

1. 确认落盘授权。
   - 讨论、临时方案对比和示例代码默认只留在对话中。
   - 用户明确要求写入，或 `checkpoint-recorder` 已判定必须保全对话中独有的实质成果时，可以创建 Draft。
   - 用户关闭本次留痕或要求只在对话中回答时，不创建 Draft，也不创建目录。

2. 判断内容类型。
   - 普通文档执行“3 个文件归组”规则。
   - 程序或可运行原型执行“第 1 个文件独立成目录”规则。

3. 轻量检查现有结构。
   - 先查看 `Drafts/` 根目录和已有主题目录的名称。
   - 优先根据目录名、文件名和必要的 frontmatter 判断主题，不要为了归类而全文扫描所有 Draft。
   - 落盘前再次查看 git 状态和目标目录，避免覆盖其他 agent 的并行改动。

4. 选择目标路径。
   - 使用稳定、明确、可搜索的业务或主题关键词。
   - 主题目录名通常不加日期；日期继续保留在普通 Draft 文件名中。
   - 普通主题目录默认只设一层，不继续细分复杂分类。
   - 程序目录可以直接位于 `Drafts/`，也可以作为已有主题目录下的二级目录。

5. 必要时移动相关文件。
   - 只移动与本次主题关系明确的文件。
   - 不要为了“清理整个仓库”批量重组历史 Draft。
   - 不确定是否同主题时，保留在根目录，不要强行归类。
   - 文件移动后，用文本搜索检查旧路径，并更新 Release 来源、灵感索引、frontmatter 和 README 中的路径引用；只修复路径，不借机改写定稿结论。

6. 处理程序生成物。
   - 不提交 `node_modules/`、虚拟环境、编译缓存、构建目录、日志或大体积临时输出。
   - 如运行程序会产生这些内容，应在程序目录内配置合适的 `.gitignore`，或使用仓库外临时目录。
   - 验证完成后，把结论写入程序目录的 `README.md` 或相关 Draft；不要只留下无法判断用途的源码。

7. 复核。
   - `Drafts/` 根目录没有平铺的程序文件。
   - 每个程序只有一个清晰的目录边界。
   - 已存在主题目录时，没有新增同主题根级 Draft。
   - 新文件触发同主题第 3 个文件时，相关文件已经归组。
   - 所有被移动文件的路径引用仍然准确。

## 不参与自动归组的内容

- `Drafts/README.md`
- `Drafts/00_灵感索引.md`
- `Drafts/private/`
- 主题不明确或关系存在歧义的文件
- 与本次任务无关、未实际触及的历史 Draft

## 示例

```text
Drafts/
├── README.md
├── 00_灵感索引.md
├── 2026-07-30_单次想法.md
├── 媒体处理/
│   ├── 2026-07-25_转码方案.md
│   ├── 2026-07-27_原文件兜底.md
│   └── 缩略图验证程序/
│       ├── README.md
│       ├── test.py
│       └── cases.json
└── 图片压缩测试程序/
    ├── README.md
    ├── test.html
    └── compress.js
```

## 禁止事项

- 不要把任何程序文件直接写到 `Drafts/` 根目录。
- 不要把一个程序拆散到多个主题目录。
- 不要为了凑满 3 个文件而创建无实际需要的 Draft。
- 不要仅凭相似词就移动语义不明确的文件。
- 不要删除 Draft；移动和归档遵循 brain 协议。
- 不要因整理 Draft 而读取或重组 `Archive/`。
- 不要把普通聊天、每个试错版本或 Record 摘要重复保存成 Draft；自动保全只保存当前有效成果和具有独立价值的备选方案。
