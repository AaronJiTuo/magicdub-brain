# magicdub-skill 项目规划

> 规划基线：2026-09-07。本文规定新项目的产品范围、分期、实现边界与验收要求；它是规划 Release，不能作为代码已实现或端到端已验收的证明。当前实际进度见 [CURRENT](../.records/CURRENT.md)。

## 1. 项目定位

`magicdub-skill` 是面向 Codex 的视频译制 skill。使用者在 Codex 中提供视频及目标语言，由 skill 自带的程序直接调用模型 API，按步骤完成转写、翻译、配音、时间轴对齐和视频合成，交付译制完成的新视频。

| 项目项 | 约定 |
| --- | --- |
| 代码仓库 | [shishengkai/magicdub-skill](https://github.com/shishengkai/magicdub-skill) |
| 当前可见性 | 私有；未来公开时间与方式未定 |
| 仓库名 | `magicdub-skill` |
| 面向用户的 skill 名 | `magicdub` |
| 首版交付形态 | 一个独立 skill，包含自身执行程序与依赖说明 |
| 首版目标平台 | Codex；不包含 DeepSeek Harness 适配 |
| 初期使用者 | 项目拥有者本人 |
| 后续受众 | 较大可能公开供其他使用者安装使用 |

仓库中文 description：

> 面向 Codex 的视频译制 Skill，通过自带程序直接调用模型 API，实现转写、翻译、配音、时间轴对齐与视频合成。

规划发布时已通过 GitHub API 回读确认仓库私有、description 一致、仓库大小为 0。创建时未初始化代码，当前尚无新 skill 的运行验收证据。

## 2. 用户场景与价值

主要场景是译制视频，用于运营抖音、YouTube 及未来可能增加的内容账号。使用者希望既能一次完成译制，也能随着工具迭代介入每个步骤，选择模型或修订内容。

当前需求来自两方面：既有 Web 交互难以快速适应个人工作方式，CLI 的可视性与操作便利性不足。新项目以 Codex 对话作为任务入口，把重复、耗时的执行交给程序；后续补充审校视图，改善文本与音视频的检查体验。

首版的核心价值是尽快得到可用成品。账号运营是使用背景，自动上传、定时发布与平台账号管理不属于首版译制链路。

## 3. 与既有 MagicDub 的关系

本项目继承 MagicDub 的译制目标：内容可懂、时间轴合理、背景音连续，人声自然并尽量保留原说话者的音色与表达。**永远不做唇形或口型修正。**

新 skill 自带执行程序，负责 API 调用、流程编排、任务状态、中间产物与合成导出。运行时不得要求安装旧 magicdub 引擎、调用旧 CLI、导入旧项目包，或通过相邻仓库路径运行旧 pipeline。语言运行时、媒体工具、供应商 API 等依赖必须明确声明。

既有 MagicDub 文档和实现可以作为产品背景或只读参考。新项目不自动继承旧 Web 方案中的 dashboard、数据库、任务队列、OSS 唯一中转、FC 合成或云部署要求；其 API 可用性也必须独立验证。

本文新增独立 skill 路线，不废弃或重写既有 Web / Cloud 路线。涉及 `magicdub-skill` 的产品形态和运行边界，以本文为准；其余旧方案仍按各自范围使用。

## 4. 首版范围

### 4.1 用户流程

1. 使用者在 Codex 中提供本地视频文件和目标语言；程序执行前明确源语言处理方式与输出位置。
2. 检查素材可读性、音轨、运行依赖和必要的 API 配置。
3. 使用一套经过验证的默认模型组合，自动执行主 pipeline。
4. 在执行期间报告当前步骤；失败时说明失败步骤和可采取的恢复动作。
5. 成功后给出可定位、可播放的译制视频，并保留该视频的项目文件与处理摘要。

首版正常路径不要求用户在每一步手动确认。缺少输入或配置时应准确说明缺口，不能把失败任务标为完成。

### 4.2 主 pipeline

| 步骤 | 职责 | 需要保留的产物 |
| --- | --- | --- |
| 输入准备 | 检查视频、记录媒体信息、提取音轨 | 原素材引用或副本、媒体信息、原音轨 |
| 人声与背景分离 | 得到供识别与配音参考使用的人声，以及可混回的背景音 | 人声轨、背景轨 |
| ASR 与时间轴 | 转写并整理句子级起止时间 | 原文、句子标识、时间轴 |
| 翻译 | 根据上下文和原句时长生成适合朗读的译文 | 译文、采用版本与关联句子 |
| 配音 | 根据译文和声音参考生成目标语言语音 | 逐句配音、实际时长 |
| 时长对齐 | 将配音安排到对应时间窗口，处理超长、过短与停顿 | 对齐参数、对齐后的片段、异常说明 |
| 混音与导出 | 将新配音与背景音混合，和原视频合成为新文件 | 成品视频、处理摘要 |

上述阶段是流程与产物边界，不要求每个阶段都使用模型，也不要求拆成多个 skill。阶段内部必须限制重试次数；时长不匹配时不能依赖无限改写和反复付费调用。

### 4.3 首版不作为交付条件的能力

- 逐阶段暂停审校、自选模型、页面编辑译文、单句重做。
- 多个 skill 或 Codex plugin 包装。
- DeepSeek Harness 或其他 harness 兼容。
- 完整时间线编辑器、多人重叠对话的完整处理、复杂声场还原。
- 公网 Web 服务、多人账号体系、自动分发到内容平台。

首个验收样本优先使用单说话人、语音清楚的短视频。后续再扩大素材复杂度；未经过测试的语言、输入格式和多人场景不得列为已支持。

## 5. 为后续分步操作保留的基础

外部先提供一次完成的体验，内部从首版起保持清楚的步骤和产物边界，避免后续审校功能要求重写整条流程。

### 5.1 每个视频有独立项目状态

项目目录保存该视频的素材信息、处理配置、原文、译文、时间轴、配音片段、执行状态和成品。目录位置与 skill 安装目录分离；具体默认路径在实现时确定。

执行进度以项目文件为准，聊天记录只承担交互。更换 Codex 任务后，应能读取项目并识别已完成的步骤、失败位置和已有产物；这不等于首版已经支持任意步骤的自动续跑。

原视频采用引用还是复制必须明确。若采用外部引用，应能发现素材失效并提示重新定位；不能把失效引用视为完整素材。

### 5.2 稳定的数据关联

首版项目数据需要表达以下信息，具体 schema 与文件名在实现设计中确定：

- 项目标识、数据格式版本、素材身份、源语言与目标语言。
- 稳定句子标识及起止时间，使原文、译文与音频片段能相互对应。
- 实际采用的供应商、具体模型及影响结果的参数。
- 各阶段状态、输入关联、输出位置、耗时和失败原因。

供应商特有响应由适配层处理，不直接成为所有后续步骤共同依赖的数据格式。

### 5.3 修改与恢复的演进规则

首版至少保留成功产物与失败位置，不因某一步失败清空整个项目。阶段续跑、文本编辑和单句重做在后续版本开放时，必须满足以下规则：

- 人工修改与模型生成版本可区分，保留恢复依据。
- 修改译文后，对应配音、对齐结果及最终合成需要重新评估有效性；不得继续把旧音频标为与新文字一致。
- 修改某一步只重做受影响的下游范围，复用前先检查输入、参数与产物是否仍匹配。
- 外部 API 返回不明确时，优先利用已保存的请求或任务标识查询状态；不能无条件重新提交付费任务。
- 数据格式升级应有版本识别与迁移策略，避免更新 skill 后旧视频项目无法继续使用。

这些是后续恢复与编辑功能的验收约束，不能将首版“文件已落盘”报告成上述功能均已实现。

## 6. 实现职责划分

| 部分 | 负责什么 |
| --- | --- |
| Skill 指令 | 引导输入、调用执行程序、解释步骤状态与产物、协调后续审校 |
| 自带执行程序 | 文件处理、流程执行、状态保存、API 请求、媒体合成与错误处理 |
| 供应商适配层 | 把具体模型的参数与响应转换成项目内部约定 |
| 视频项目文件 | 保存可复用的素材、文本、时间轴、配置与执行结果 |
| 后续审校视图 | 展示对照和试听入口，把编辑结果保存回同一项目 |

程序语言、包管理工具、具体安装布局及审校页技术方案尚未落定。Python、uv 和 HTML / JS 等讨论建议保存在 [实现选项草稿](../Drafts/magicdub-skills/2026-09-07_magicdub-skill实现选项与待决事项.md)，不作为本文已确认的技术栈。

首版自动流程不要求提供 Web server。后续审校视图是明确的功能增量，不能假定安装 skill 就会自动获得页面；具体打开方式与持久化交互需要做原型验证。

## 7. 迭代顺序

以下是功能阶段，具体版本号与日期未定。

| 阶段 | 交付重点 | 完成标准 |
| --- | --- | --- |
| 首版：自动译制 | 一个主 skill、一套默认模型组合、从视频到成品 | 通过第 8 节验收，能够用于一次真实个人译制任务 |
| 第二阶段：分步控制 | 停在指定步骤、读取中间结果、修改文本、恢复或重做 | 修改能可靠传到后续输出，不无故重跑无关步骤 |
| 第三阶段：模型选择 | 按 ASR、翻译、TTS 等阶段选择已支持的模型 | 更换一个阶段的模型不要求改写其他阶段；实际选择被记录 |
| 后续：可视审校与公开分发 | 对照、逐句试听、异常定位，以及其他使用者的安装体验 | 编辑结果保存可靠；在支持环境中完成独立安装与真实译制 |

Whisper 与 Fun-ASR 是用户提出的未来 ASR 选择示例，不代表首版必须同时支持，也不代表已选定其供应商或模型版本。审校页可以按真实使用反馈提前，但不阻塞首版自动链路。

保持一个主 skill，直到出现可以独立使用和验收的额外工作流。是否增加 plugin 包装由后续安装与扩展需求决定；公开使用不构成预先开发 plugin 的要求。

## 8. 首版验收

验收必须使用新仓库自身程序和真实 API 调用。旧 magicdub 的历史运行结果、规划文档、模拟输出均不能替代本项目验收。

| 检查项 | 通过要求 |
| --- | --- |
| 独立运行 | 在声明的环境中，仅依靠新 skill 与其声明依赖完成流程，不需要旧引擎或个人相邻仓库 |
| 真实闭环 | 在 Codex 中提供一段基准视频与目标语言后，生成并定位译制完成的新视频 |
| 媒体完整 | 成品可播放、音视频轨道有效，原视频画面与完整时长得到保留，尾句未被意外截断 |
| 译制质量 | 全片试听确认内容可懂、无明显漏句或错配；配音时序合理，背景音连续且无明显原语音叠播 |
| 可追溯 | 项目中能找到原文、译文、时间轴、片段及实际模型信息，并对应到成品 |
| 失败可定位 | 配置缺失和至少一次阶段失败能得到明确状态；已有成功产物保留，失败未被标成完成 |
| 输入与费用保护 | 不覆盖原素材；重试有上限，记录调用耗时及可获得的用量或费用信息，估算值与实账可区分 |
| 边界准确 | 验收记录列出实际测试的语言、素材、运行环境与已知限制，不扩大为未测场景的支持承诺 |

验收记录还应保存代码版本、样本标识、输出位置和人工试听结论。时间轴误差、可接受变速范围等具体阈值，在固定样本后根据实测确定并写入验收标准，不能在没有测量时宣称达标。

## 9. 面向后续公开的准备

首版仍以自用效果为先，但安装与配置不能绑定作者电脑的绝对路径、个人账号或旧项目虚拟环境。依赖与配置说明随 skill 分发，凭证由使用者配置，不进入仓库、示例文件或前端资源。

从首版起记录影响复现的模型、程序版本和参数。可获得的调用用量与成本应可查询，便于实际运营时比较质量、耗时与费用。

公开前再确定支持系统、安装分发方式、许可证和发布流程，并用其他使用者的配置验证安装。未来对抖音、YouTube 或其他账号的语言风格、术语和输出规格差异，可以通过后续配置扩展；首版无需实现账号管理。

## 10. 下一步实施顺序

1. 在 `magicdub-skill` 实现任务中收敛程序语言、运行环境、项目目录和依赖安装方式，并更新相应技术设计。
2. 选定一段真实基准视频、源语言与目标语言，明确 API 预算和首版实际支持范围。
3. 每个外部处理阶段先选一个供应商，核对当前 API、具体 model ID、输入输出限制及计费；需要上传媒体时明确临时传输与结果落盘方式。
4. 定义最小项目数据格式和阶段接口，实现自动主链路，再接入 skill 的输入、执行和结果交付流程。
5. 按第 8 节完成真实验收，保存证据；根据第一次实际译制中暴露的问题安排分步编辑与审校能力。

本规划完成代表产品方向与开发顺序已经形成可交接文档，项目代码仍待实现。
